# Compression Care Worker — System Design

## Overview

A Node.js worker service that processes medical referral and shipping notification emails from Gmail. It listens for jobs on a Redis queue (BullMQ), fetches emails via the Gmail API, extracts structured data from multi-format attachments (PDFs, DOCX, images, spreadsheets), analyzes content with OpenAI, and persists results to MongoDB.

The service is designed to run as a background worker — it does not expose an HTTP API. A separate producer service enqueues Gmail message IDs into Redis; this worker consumes them.

## Key Services

### `EmailProcessorService` (`src/services/email-processor.service.js`)
Main orchestrator. Initializes all sub-services, starts the BullMQ worker, and coordinates the full processing pipeline for each job.

- Connects to Redis and MongoDB on startup
- Worker concurrency is configurable via `WORKER_CONCURRENCY` env var (default 5)
- On job failure, removes message ID from Redis ZSET so the producer can re-enqueue it
- Handles graceful shutdown: closes worker, drains connections

### `GmailService` (`src/services/gmail.service.js`)
Gmail API v1 integration layer. Handles OAuth 2.0 authentication, email fetching, attachment downloads, and read-state management.

- OAuth credentials stored in `token.json` (generated by `npm run auth`)
- `credentialsv2.json` holds Google Cloud OAuth client config (not in git)
- Supports Gmail Pub/Sub watch setup (expires every 7 days — see `PUBSUB_SETUP.md`)

### `ContentExtractorService` (`src/services/content-extractor.service.js`)
Multi-format content extraction. Returns a normalized object consumed by `OpenAIService`.

Output shape:
```js
{
  emailId, subject, from, date,
  textContent: "email body as plain text",
  attachmentContents: [{ filename, content: "extracted text" }],
  images: [{ filename, base64, mimeType, fax }],
  faxattachments: [{ filename, url: "cloudinary_url", mimeType }]
}
```

Scanned/image-based PDFs are orientation-corrected and uploaded to Cloudinary before being sent to OpenAI via the Response API.

### `OpenAIService` (`src/services/openai.service.js`)
AI extraction layer. Classifies each email into one of three categories and extracts structured data.

**Classifications:**
- `not_relevant` — promotional emails, newsletters, spam; no data extracted
- `patient` — medical referrals, prescriptions, compression garment orders; returns one patient object
- `shipment` — manufacturer notifications, tracking updates; returns array of shipment objects

**Models used:**
- `gpt-4.1-mini` — Chat Completions API for text and image inputs
- `gpt-5` — Response API for file-based (Cloudinary-hosted) PDF inputs

**Patient fields:** `patient_first/last_name`, `patient_address`, `patient_gender`, `patient_date_of_birth`, `patient_email_address`, `primary/secondary/tertiary_insurance`, `product_ordered`, `therapist` (name + email), `primary_care_physician`, `extraction_warnings`

**Shipment fields:** `source`, `ship_date`, `shipper`, `tracking_number`, `order_number`, `referral_status`, `line_items` (sku, description, quantity), `extraction_warnings`

### `CloudinaryService` (`src/services/cloudinary.service.js`)
Upload and delete PDFs in Cloudinary. Used exclusively for scanned PDFs that exceed what can be sent as base64 to OpenAI.

## Data Flow Summary

1. Producer enqueues `{ messageId }` into `gmail-message-queue` Redis queue
2. BullMQ worker picks up the job
3. `GmailService` fetches full email (headers, body, attachments)
4. `ContentExtractorService` extracts text from all parts/attachments; scanned PDFs go to Cloudinary
5. `OpenAIService` receives extracted content, calls appropriate OpenAI endpoint, returns classification + structured data
6. `EmailProcessorService` saves result to MongoDB, marks email as read in Gmail, cleans up Redis ZSET
7. On failure: message ID is removed from ZSET, allowing re-enqueue by producer

## External Integrations

| Service | Purpose | Auth |
|---|---|---|
| Gmail API v1 | Email fetch, attachment download, mark-as-read | OAuth 2.0 (`token.json`) |
| Google Cloud Pub/Sub | Push notifications for new emails (optional) | Service account |
| OpenAI API | Data classification and extraction | `OPENAI_API_KEY` |
| Redis (BullMQ) | Job queue and processed-email ZSET | Password (`REDIS_PASS`) |
| MongoDB | Persist extraction results | Connection string (`MONGODB_URI`) |
| Cloudinary | Cloud hosting for scanned PDFs | API key + secret |


## Environment Variables

| Variable | Purpose |
|---|---|
| `OPENAI_API_KEY` | OpenAI API access |
| `REDIS_HOST / REDIS_PORT / REDIS_PASS` | Redis connection |
| `REDIS_QUEUE_NAME` | BullMQ queue name (default: `gmail-message-queue`) |
| `MONGODB_URI / MONGODB_DB / MONGODB_COLLECTION` | MongoDB connection |
| `CLOUDINARY_CLOUD_NAME / CLOUDINARY_API_KEY / CLOUDINARY_API_SECRET` | Cloudinary credentials |
| `GMAIL_PUBSUB_TOPIC` | Google Cloud Pub/Sub topic for Gmail watch |
| `WORKER_CONCURRENCY` | Number of parallel jobs (default: 5) |
| `CHECK_INTERVAL_MS` | Polling interval if not using Pub/Sub |
| `MAX_EMAILS_PER_CHECK` | Max emails fetched per poll cycle |

## Notes

- All services are singletons (module-level exports), initialized once at startup
- An email is always classified as exactly one type: `not_relevant`, `patient`, or `shipment` — never both
- Gmail watch via Pub/Sub expires every 7 days; the watch must be renewed (see `PUBSUB_SETUP.md`)
- `credentialsv2.json` and `token.json` are not committed to git; generate them via `npm run auth`
